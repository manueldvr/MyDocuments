# 1 - Core Java 17


## 1. Generics

Generics allow classes, interfaces, and methods to work with different types while maintaining compile-time type safety.

```java
List<String> names = new ArrayList<>();

names.add("Alice");
// names.add(10); // Compilation error

String name = names.get(0); // No explicit cast required
```

Without generics, collections would usually store `Object`, requiring casts and moving many errors from compilation to runtime.

### Type erasure

Java implements generics using **type erasure**. Generic type information is primarily used by the compiler and mostly removed from the generated bytecode.

For example:

```java
List<String> names = new ArrayList<>();
List<Integer> numbers = new ArrayList<>();
```

At runtime, both objects are essentially instances of `ArrayList`. The JVM generally does not maintain separate classes such as `ArrayList<String>` and `ArrayList<Integer>`.

Conceptually:

```java
class Box<T> {
    private T value;

    public T getValue() {
        return value;
    }
}
```

After erasure behaves approximately like:

```java
class Box {
    private Object value;

    public Object getValue() {
        return value;
    }
}
```

The compiler inserts the necessary casts at usage points.

When a type is bounded:

```java
class NumericBox<T extends Number> {
    private T value;
}
```

`T` is erased to its upper bound, `Number`, rather than `Object`.

Important consequences:

```java
// Not allowed:
if (value instanceof T) { }

// Not allowed:
T value = new T();

// Not allowed:
List<String>[] array = new List<String>[10];

// Not allowed because both have the same erased signature:
// void process(List<String> values)
// void process(List<Integer> values)
```

Generic type arguments also cannot be primitive types:

```java
List<Integer> numbers = new ArrayList<>(); // Wrapper required
// List<int> numbers;                      // Invalid
```

### Invariance

Java generics are invariant. Even though `Integer` extends `Number`, this does not mean `List<Integer>` extends `List<Number>`.

```java
List<Integer> integers = List.of(1, 2, 3);

// Invalid:
// List<Number> numbers = integers;
```

If it were allowed, someone could insert a `Double` into a list that is supposed to contain only integers.

Wildcards provide controlled covariance and contravariance.

### Upper-bounded wildcard: `? extends T`

An upper-bounded wildcard accepts collections whose element type is `T` or a subclass of `T`.

```java
public double sum(List<? extends Number> numbers) {
    double total = 0;

    for (Number number : numbers) {
        total += number.doubleValue();
    }

    return total;
}
```

This method accepts:

```java
List<Integer> integers = List.of(1, 2, 3);
List<Double> doubles = List.of(1.5, 2.5);

sum(integers);
sum(doubles);
```

You can safely read elements as `Number`, but you generally cannot add elements:

```java
void process(List<? extends Number> numbers) {
    Number number = numbers.get(0); // Safe

    // numbers.add(10);   // Invalid
    // numbers.add(2.5);  // Invalid
}
```

The compiler does not know whether the actual list is a `List<Integer>`, `List<Double>`, or another subtype.

### Lower-bounded wildcard: `? super T`

A lower-bounded wildcard accepts collections whose element type is `T` or one of its supertypes.

```java
public void addIntegers(List<? super Integer> destination) {
    destination.add(10);
    destination.add(20);
}
```

It accepts:

```java
List<Integer> integers = new ArrayList<>();
List<Number> numbers = new ArrayList<>();
List<Object> objects = new ArrayList<>();

addIntegers(integers);
addIntegers(numbers);
addIntegers(objects);
```

Writing `Integer` values is safe, but values can only be read reliably as `Object`:

```java
Object value = destination.get(0);
```

### PECS

PECS means:

> Producer Extends, Consumer Super.

Use `? extends T` when a structure **produces values** that your method reads:

```java
public double calculateTotal(List<? extends Number> source) {
    return source.stream()
            .mapToDouble(Number::doubleValue)
            .sum();
}
```

Use `? super T` when a structure **consumes values** that your method writes:

```java
public void copyIntegers(
        List<? extends Integer> source,
        List<? super Integer> destination
) {
    destination.addAll(source);
}
```

This principle is visible in the JDK:

```java
public static <T> void copy(
        List<? super T> destination,
        List<? extends T> source
)
```

A practical summary:

| Declaration         | Read as  | Can safely add         |
| ------------------- | -------- | ---------------------- |
| `List<T>`           | `T`      | `T`                    |
| `List<? extends T>` | `T`      | Nothing except `null`  |
| `List<? super T>`   | `Object` | `T` and its subclasses |
| `List<?>`           | `Object` | Nothing except `null`  |

### Generic methods

A generic method declares its own type parameter before the return type:

```java
public static <T> T first(List<T> values) {
    if (values.isEmpty()) {
        throw new IllegalArgumentException("List cannot be empty");
    }

    return values.get(0);
}
```

Usage:

```java
String firstName = first(List.of("Alice", "Bob"));
Integer firstNumber = first(List.of(10, 20));
```

The compiler normally infers `T`.

Generic methods can also have bounds:

```java
public static <T extends Comparable<? super T>> T maximum(
        List<? extends T> values
) {
    return values.stream()
            .max(Comparator.naturalOrder())
            .orElseThrow();
}
```

The bound means that `T` must be comparable to itself or one of its supertypes.

## 2. Collections Internals

The Java Collections Framework provides common data structures such as lists, sets, queues, and maps.

Choosing a collection should depend on required operations, ordering, concurrency, memory usage, and algorithmic cost—not merely on familiarity.

### `HashMap`

A `HashMap<K,V>` stores entries in an internal array of buckets.

Conceptually:

```text
hash(key)
   ↓
spread hash bits
   ↓
calculate bucket index
   ↓
search entries in that bucket
```

The bucket index is effectively calculated from the hash and the table capacity.

```java
Map<String, Integer> ages = new HashMap<>();

ages.put("Alice", 35);
ages.put("Bob", 42);
```

A bucket can contain multiple entries when different keys map to the same bucket. This is a **hash collision**.

Since Java 8, heavily populated buckets can be transformed from linked structures into balanced red-black trees, provided certain capacity and collision thresholds are met. This improves pathological lookup behavior.

Typical complexity:

| Operation |              Average |             Pathological/worst case |
| --------- | -------------------: | ----------------------------------: |
| `get`     |               `O(1)` |     `O(log n)` in treeified buckets |
| `put`     |     `O(1)` amortized | Can be more expensive during resize |
| `remove`  |       `O(1)` average |               Depends on collisions |
| Iteration | `O(capacity + size)` |                                   — |

`HashMap`:

* allows one `null` key;
* allows `null` values;
* does not guarantee iteration order;
* is not thread-safe.

### Resizing

A `HashMap` has:

* a capacity: the bucket-array size;
* a load factor: normally `0.75`;
* a resize threshold: approximately `capacity × load factor`.

When the number of entries passes the threshold, the table generally grows to twice its previous capacity, and entries are redistributed.

Resizing is expensive because it involves allocating a new table and relocating bucket entries. Individual `put()` operations are normally constant time, but a resize operation is `O(n)`.

If the expected size is known, provide a suitable initial capacity:

```java
Map<Long, User> users = new HashMap<>(1_024);
```

This can reduce repeated resizing. However, excessive initial capacity wastes memory and makes iteration more expensive.

In Java 17, if you expect `n` entries with the standard load factor, the required table capacity is approximately:

```text
ceil(n / 0.75)
```

### The `equals()` and `hashCode()` contract

Hash-based collections depend on both methods:

```java
HashMap
HashSet
ConcurrentHashMap
```

The essential contract is:

1. If `a.equals(b)` is `true`, then `a.hashCode()` must equal `b.hashCode()`.
2. Two objects with the same hash code do not necessarily have to be equal.
3. `equals()` should be reflexive, symmetric, transitive, consistent, and return `false` for `null`.
4. Values used by `equals()` and `hashCode()` should remain stable while the object is stored as a hash key.

Example:

```java
public final class CustomerKey {

    private final String country;
    private final long customerNumber;

    public CustomerKey(String country, long customerNumber) {
        this.country = country;
        this.customerNumber = customerNumber;
    }

    @Override
    public boolean equals(Object object) {
        if (this == object) {
            return true;
        }

        if (!(object instanceof CustomerKey other)) {
            return false;
        }

        return customerNumber == other.customerNumber
                && Objects.equals(country, other.country);
    }

    @Override
    public int hashCode() {
        return Objects.hash(country, customerNumber);
    }
}
```

Java records automatically generate appropriate implementations:

```java
public record CustomerKey(String country, long customerNumber) {}
```

A dangerous design is a mutable key:

```java
Map<CustomerKey, String> map = new HashMap<>();

map.put(key, "customer");

// If a field participating in hashCode is modified here,
// map.get(key) may no longer find the entry.
```

Although the entry remains in its original bucket, its new hash may point to a different bucket.

### `ConcurrentHashMap`

`ConcurrentHashMap` is designed for concurrent access:

```java
ConcurrentMap<String, Long> counters = new ConcurrentHashMap<>();
```

Unlike older implementations based on a single map-wide lock, modern `ConcurrentHashMap` implementations combine techniques such as:

* volatile reads;
* compare-and-set operations;
* fine-grained synchronization on contested buckets;
* cooperative resizing;
* tree structures for highly contended/colliding buckets.

It does not lock the entire map for every operation.

Unlike `HashMap`, it does not allow `null` keys or values. In concurrent code, `null` would be ambiguous: it could mean either “absent” or “mapped to null.”

Composite actions must be atomic. This is unsafe:

```java
if (!map.containsKey(key)) {
    map.put(key, createValue());
}
```

Another thread could modify the map between the two calls.

Prefer atomic map operations:

```java
map.putIfAbsent(key, value);

map.computeIfAbsent(key, ignored -> createValue());

map.merge(key, 1L, Long::sum);

map.compute(key, (ignored, oldValue) ->
        oldValue == null ? 1L : oldValue + 1
);
```

Be cautious with mapping functions passed to `compute*()`: they should be short and should avoid recursive modifications or slow blocking work where possible.

### Iteration behavior and costs

Different collections have different iteration characteristics:

| Collection             | Iteration characteristics                      |
| ---------------------- | ---------------------------------------------- |
| `ArrayList`            | Fast sequential access; cache-friendly         |
| `LinkedList`           | Pointer traversal; usually less cache-friendly |
| `HashMap` / `HashSet`  | Cost depends on capacity plus size             |
| `LinkedHashMap`        | Predictable insertion/access order             |
| `TreeMap` / `TreeSet`  | Sorted order; traversal is `O(n)`              |
| `ConcurrentHashMap`    | Weakly consistent concurrent iteration         |
| `CopyOnWriteArrayList` | Snapshot iteration; writes are expensive       |

Most regular collection iterators are fail-fast:

```java
for (String value : values) {
    values.remove(value); // May cause ConcurrentModificationException
}
```

Use the iterator’s own removal operation when supported:

```java
Iterator<String> iterator = values.iterator();

while (iterator.hasNext()) {
    String value = iterator.next();

    if (value.isBlank()) {
        iterator.remove();
    }
}
```

Fail-fast behavior is for bug detection; it is not a synchronization mechanism or a guaranteed concurrent-safety feature.

`ConcurrentHashMap` iterators are weakly consistent: they do not normally throw `ConcurrentModificationException`, and they may observe some concurrent updates without providing a single frozen snapshot.

## 3. Annotations

Annotations attach metadata to program elements such as classes, methods, constructors, fields, parameters, packages, and type uses.

```java
@Override
public String toString() {
    return "Customer";
}
```

An annotation does not automatically execute behavior. Some component must interpret it, such as:

* the Java compiler;
* an annotation processor;
* reflection-based framework code;
* a bytecode enhancement tool;
* the JVM.

### Defining an annotation

```java
public @interface Auditable {

    String action();

    boolean includeArguments() default false;
}
```

Usage:

```java
@Auditable(action = "CREATE_PAYMENT", includeArguments = true)
public Payment createPayment(PaymentRequest request) {
    // ...
}
```

### Meta-annotations

Meta-annotations are annotations applied to other annotations.

#### `@Target`

Defines where the annotation may be used:

```java
@Target(ElementType.METHOD)
public @interface Auditable {}
```

Common targets include:

```java
TYPE
METHOD
FIELD
CONSTRUCTOR
PARAMETER
ANNOTATION_TYPE
TYPE_USE
```

#### `@Retention`

Defines how long the annotation is retained:

```java
@Retention(RetentionPolicy.RUNTIME)
public @interface Auditable {}
```

Retention options:

| Policy    | Available in source | In class file | Available through runtime reflection |
| --------- | ------------------: | ------------: | -----------------------------------: |
| `SOURCE`  |                 Yes |            No |                                   No |
| `CLASS`   |                 Yes |           Yes |                          Normally no |
| `RUNTIME` |                 Yes |           Yes |                                  Yes |

Frameworks that inspect annotations at runtime usually require `RUNTIME`.

#### `@Inherited`

Allows a class-level annotation to be inherited by subclasses:

```java
@Inherited
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
public @interface Monitored {}
```

Its behavior is limited:

* applies to class inheritance;
* does not automatically work for method annotations;
* does not cause annotations on interfaces to be inherited in the same manner.

#### `@Documented`

Includes the annotation in generated Javadoc.

#### `@Repeatable`

Allows an annotation to appear more than once:

```java
@Repeatable(RolesAllowed.class)
public @interface RoleAllowed {
    String value();
}
```

### Composed annotations

Frameworks often combine multiple annotations into a custom annotation:

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component
@Transactional
public @interface TransactionalService {}
```

Usage:

```java
@TransactionalService
public class PaymentService {
}
```

Whether meta-annotation composition is recognized depends on the framework. Spring has extensive support for composed annotations.

### Common framework use cases

Annotations are widely used for:

* dependency injection: `@Component`, `@Autowired`, `@Inject`;
* transactions: `@Transactional`;
* validation: `@NotNull`, `@Size`, `@Valid`;
* REST mapping: `@RestController`, `@GetMapping`;
* persistence mapping: `@Entity`, `@Id`, `@OneToMany`;
* serialization: `@JsonProperty`, `@JsonIgnore`;
* testing: `@Test`, `@BeforeEach`;
* code generation and compile-time checks.

Framework behavior may be implemented through reflection, generated code, proxies, or bytecode manipulation. Therefore, seeing an annotation does not by itself explain when or how the behavior occurs.

## 4. Reflection

Reflection allows Java code to examine and interact with classes, constructors, methods, fields, and annotations at runtime.

```java
Class<?> type = Class.forName("com.example.PaymentService");
```

Frameworks use reflection for dependency injection, object mapping, persistence, testing, serialization, and plugin discovery.

### Creating instances

The preferred modern approach is to obtain and invoke a constructor:

```java
Class<?> type = Class.forName("com.example.Customer");

Constructor<?> constructor =
        type.getDeclaredConstructor(String.class, long.class);

Object customer = constructor.newInstance("Alice", 100L);
```

For a typed class:

```java
Class<Customer> type = Customer.class;

Constructor<Customer> constructor =
        type.getDeclaredConstructor(String.class, long.class);

Customer customer = constructor.newInstance("Alice", 100L);
```

The older `Class.newInstance()` method is deprecated because it handles constructor exceptions poorly and only supports an accessible no-argument constructor.

### Invoking methods

```java
Method method = Customer.class.getDeclaredMethod(
        "changeName",
        String.class
);

method.invoke(customer, "Bob");
```

For a static method, the target instance is `null`:

```java
Method method = Calculator.class.getDeclaredMethod(
        "sum",
        int.class,
        int.class
);

Object result = method.invoke(null, 10, 20);
```

Reflection wraps an exception thrown by the invoked method in `InvocationTargetException`:

```java
try {
    method.invoke(target);
} catch (InvocationTargetException exception) {
    Throwable originalCause = exception.getCause();
}
```

### Invoking constructors

```java
Constructor<Payment> constructor =
        Payment.class.getDeclaredConstructor(
                BigDecimal.class,
                Currency.class
        );

Payment payment = constructor.newInstance(
        new BigDecimal("100.00"),
        Currency.getInstance("USD")
);
```

### Access control and modules

Code sometimes attempts to access private members:

```java
Field field = Customer.class.getDeclaredField("name");
field.setAccessible(true);
field.set(customer, "Bob");
```

This creates several problems:

* breaks encapsulation;
* increases coupling to implementation details;
* may fail under Java’s module system;
* can require `--add-opens`;
* can produce illegal reflective-access or inaccessible-object errors;
* may stop working after internal refactoring.

Java 17 strongly encapsulates many JDK internals. Reflective access that worked in older Java versions may now fail with `InaccessibleObjectException`.

### Performance

Reflection is generally slower than direct invocation because it involves:

* metadata lookup;
* access checks;
* dynamic argument handling;
* boxing and unboxing;
* reduced opportunities for compiler optimization.

Avoid repeatedly looking up the same member:

```java
// Inefficient if executed for every item:
Method method = type.getDeclaredMethod("getId");
```

Cache reflective metadata when it is safe:

```java
private static final Method GET_ID_METHOD = findGetIdMethod();
```

For high-performance dynamic invocation, alternatives include:

* `MethodHandle`;
* `VarHandle`;
* generated bytecode;
* compile-time annotation processing;
* code-generation libraries.

Performance should still be measured. Reflection overhead may be negligible compared with database, network, or file-system operations.

### Security and maintenance risks

Reflection can:

* bypass intended APIs and invariants;
* expose sensitive fields;
* create unexpected objects;
* invoke dangerous functionality;
* make code harder to analyze and refactor;
* enlarge attack surfaces when class or method names come from untrusted input.

Dangerous pattern:

```java
String className = request.getParameter("class");
Class<?> type = Class.forName(className);
Object object = type.getDeclaredConstructor().newInstance();
```

Untrusted input should never freely determine which classes or methods are loaded. Use an explicit allowlist or a controlled registry.

## 5. Serialization

Serialization transforms object state into a format that can be stored or transferred. Java’s native object serialization uses `Serializable` and `Externalizable`.

### `Serializable`

`Serializable` is a marker interface:

```java
public class Customer implements Serializable {

    private static final long serialVersionUID = 1L;

    private String name;
    private long customerNumber;
}
```

It does not declare methods. `ObjectOutputStream` and `ObjectInputStream` handle the process:

```java
try (ObjectOutputStream output =
             new ObjectOutputStream(new FileOutputStream("customer.bin"))) {
    output.writeObject(customer);
}
```

Deserialization:

```java
try (ObjectInputStream input =
             new ObjectInputStream(new FileInputStream("customer.bin"))) {
    Customer customer = (Customer) input.readObject();
}
```

Fields marked `transient` are excluded from default serialization:

```java
private transient String temporaryToken;
```

Static fields are also not part of an individual object’s serialized state.

During deserialization, constructors of serializable classes are generally not executed in the normal way. This can bypass constructor-based validation and invariants.

### `serialVersionUID`

`serialVersionUID` identifies a serializable class version:

```java
private static final long serialVersionUID = 1L;
```

If it is not explicitly declared, the compiler/JVM derives one from class details. Minor structural changes can then unexpectedly break compatibility.

A mismatch may cause:

```text
InvalidClassException
```

Declaring it explicitly gives the developer control, but does not guarantee semantic compatibility. You must still manage field changes and object invariants carefully.

### `Externalizable`

`Externalizable` extends `Serializable` and gives the class full control over the serialized format:

```java
public class Customer implements Externalizable {

    private String name;
    private long customerNumber;

    public Customer() {
        // Required public no-argument constructor
    }

    @Override
    public void writeExternal(ObjectOutput output) throws IOException {
        output.writeUTF(name);
        output.writeLong(customerNumber);
    }

    @Override
    public void readExternal(ObjectInput input)
            throws IOException, ClassNotFoundException {
        this.name = input.readUTF();
        this.customerNumber = input.readLong();
    }
}
```

Comparison:

| Aspect                       | `Serializable`        | `Externalizable`            |
| ---------------------------- | --------------------- | --------------------------- |
| Implementation effort        | Low                   | Higher                      |
| Control over format          | Limited by default    | Complete                    |
| No-argument constructor      | Not normally required | Public constructor required |
| Field handling               | Mostly automatic      | Fully manual                |
| Compatibility responsibility | Partial               | Entirely developer-managed  |

### Compatibility pitfalls

Java native serialization tightly couples serialized data to Java class structure.

Problems can occur when:

* classes are renamed or moved;
* fields change type;
* inheritance changes;
* `serialVersionUID` changes;
* different application versions exchange objects;
* a required class is missing from the receiving application.

For long-term storage or service-to-service contracts, formats such as JSON, Protocol Buffers, Avro, or MessagePack are usually better choices because they offer more explicit schemas and better interoperability.

### Security pitfalls

Deserializing untrusted Java serialization data is dangerous. Object graphs may trigger code execution through methods such as:

* `readObject`;
* `readResolve`;
* validation callbacks;
* code in chained library classes.

Do not deserialize arbitrary native Java objects received from unknown clients.

If native serialization is unavoidable:

* accept data only from trusted sources;
* use `ObjectInputFilter`;
* allowlist expected classes;
* reject unexpectedly deep or large object graphs;
* keep dependencies patched;
* isolate deserialization;
* authenticate and integrity-protect serialized data.

Example filter:

```java
ObjectInputFilter filter =
        ObjectInputFilter.Config.createFilter(
                "com.example.dto.*;java.base/*;!*"
        );

input.setObjectInputFilter(filter);
```

Even with filters, native Java serialization should not be the default format for public APIs.

## 6. IO vs NIO

Classic Java IO is mostly stream-oriented, while NIO introduces buffers, channels, selectors, and more extensive file-system APIs.

### Traditional IO

Classic IO uses `InputStream`, `OutputStream`, `Reader`, and `Writer`.

```java
try (InputStream input = new FileInputStream("data.bin")) {
    byte[] buffer = new byte[8_192];

    int bytesRead;
    while ((bytesRead = input.read(buffer)) != -1) {
        process(buffer, bytesRead);
    }
}
```

For text:

```java
try (BufferedReader reader =
             Files.newBufferedReader(Path.of("data.txt"))) {
    String line;

    while ((line = reader.readLine()) != null) {
        System.out.println(line);
    }
}
```

Traditional blocking IO is often the simplest and most appropriate option for:

* normal file processing;
* small numbers of socket connections;
* batch applications;
* command-line tools;
* workloads where one thread per active connection is acceptable.

### NIO channels

A channel represents a connection to an IO-capable resource:

```java
try (FileChannel channel = FileChannel.open(
        Path.of("data.bin"),
        StandardOpenOption.READ
)) {
    ByteBuffer buffer = ByteBuffer.allocate(8_192);

    while (channel.read(buffer) != -1) {
        buffer.flip();

        while (buffer.hasRemaining()) {
            byte value = buffer.get();
            process(value);
        }

        buffer.clear();
    }
}
```

Channels may support:

* reading and writing;
* random file access;
* transfers between channels;
* non-blocking operation for supported channel types.

### Buffers

A `Buffer` stores data being moved between application code and a channel.

The main properties are:

* `capacity`: total buffer size;
* `position`: next read or write location;
* `limit`: boundary that must not be crossed.

Typical cycle:

```java
channel.read(buffer); // Writes bytes into buffer
buffer.flip();        // Changes from write mode to read mode
process(buffer);      // Reads bytes
buffer.clear();       // Prepares for another write
```

`flip()` does not flip the bytes. It sets the limit to the current position and moves the position to zero.

Common buffer types include:

```java
ByteBuffer
CharBuffer
IntBuffer
LongBuffer
```

A direct byte buffer may be allocated outside the ordinary Java heap:

```java
ByteBuffer buffer = ByteBuffer.allocateDirect(8_192);
```

Direct buffers can reduce copying for native IO but are more expensive to allocate and manage. They should not be used automatically without measurement.

### Selectors

A selector lets one thread monitor multiple non-blocking channels for readiness events.

```java
Selector selector = Selector.open();

serverChannel.configureBlocking(false);
serverChannel.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();

    Iterator<SelectionKey> keys =
            selector.selectedKeys().iterator();

    while (keys.hasNext()) {
        SelectionKey key = keys.next();
        keys.remove();

        if (key.isAcceptable()) {
            acceptConnection(key);
        } else if (key.isReadable()) {
            readData(key);
        } else if (key.isWritable()) {
            writeData(key);
        }
    }
}
```

This architecture avoids allocating a dedicated platform thread for every mostly idle network connection.

### When non-blocking IO matters

Non-blocking IO is useful when an application handles:

* many simultaneous connections;
* connections that remain idle for long periods;
* chat or WebSocket servers;
* gateways and proxies;
* event-driven network servers;
* workloads where thread-per-connection consumes too much memory.

It offers fewer blocked threads, but introduces:

* more complex state management;
* partial reads and writes;
* backpressure concerns;
* event-loop blocking risks;
* harder debugging.

For ordinary file access or a moderate number of requests, blocking IO may remain simpler and perfectly adequate.

Also distinguish non-blocking from asynchronous execution. Sending blocking IO to another thread does not make the underlying operation non-blocking; it merely moves where the blocking occurs.

## 7. Logging

Logging records application events for debugging, auditing, monitoring, and incident investigation.

In Java applications, a common arrangement is:

* application code uses the SLF4J API;
* Logback or Log4j 2 provides the implementation;
* logs are collected by a centralized platform.

```java
private static final Logger log =
        LoggerFactory.getLogger(PaymentService.class);
```

### Logging levels

Common levels ordered from least to most severe:

```text
TRACE < DEBUG < INFO < WARN < ERROR
```

Typical meaning:

| Level   | Intended use                                              |
| ------- | --------------------------------------------------------- |
| `TRACE` | Extremely detailed execution flow                         |
| `DEBUG` | Diagnostic information for developers                     |
| `INFO`  | Relevant normal business or lifecycle event               |
| `WARN`  | Unexpected condition from which the application recovered |
| `ERROR` | Operation failed and requires investigation               |

Example:

```java
log.debug("Calculating payment for customerId={}", customerId);
log.info("Payment created paymentId={} amount={}", paymentId, amount);
log.warn("Payment provider response was slow provider={}", provider);
log.error("Payment creation failed paymentId={}", paymentId, exception);
```

Avoid string concatenation:

```java
// Avoid:
log.debug("Customer ID: " + customerId);

// Prefer:
log.debug("Customer ID: {}", customerId);
```

Parameterized logging avoids constructing the message unnecessarily when the level is disabled.

### Appenders

An appender sends log events to a destination.

Common destinations include:

* console;
* files;
* rolling files;
* remote log collectors;
* syslog;
* asynchronous queues.

A rolling-file appender can rotate files based on:

* file size;
* date;
* retention period;
* total storage usage.

In containers, logging to standard output is usually preferred. The container platform collects and forwards the logs.

Asynchronous appenders can reduce request-thread latency, but require decisions about:

* queue capacity;
* event loss when the queue is full;
* shutdown flushing;
* memory usage;
* ordering.

### Structured logging

Plain-text logs are convenient for humans:

```text
Payment created for customer 102 with amount 250.00
```

Structured logs represent fields explicitly, commonly as JSON:

```json
{
  "timestamp": "2026-08-02T12:30:45.123Z",
  "level": "INFO",
  "service": "payment-service",
  "event": "payment_created",
  "paymentId": "pay-7821",
  "customerId": "102",
  "amount": 250.00,
  "currency": "USD",
  "correlationId": "req-c81f2"
}
```

Benefits include:

* reliable searching and filtering;
* aggregation by fields;
* dashboards and alerts;
* easier machine processing;
* fewer fragile text-parsing rules.

Use consistent names and types. For example, do not sometimes log `customerId` as a number and elsewhere as a nested object.

Never log sensitive information such as:

* passwords;
* authentication tokens;
* session IDs;
* private keys;
* complete payment-card data;
* unnecessary personal data.

### Correlation IDs across services

In distributed systems, a single business request may cross several services:

```text
Client → API Gateway → Order Service → Payment Service → Database
```

A correlation ID gives all logs belonging to that flow a shared identifier.

For example, an inbound HTTP request may contain:

```http
X-Correlation-ID: 8ab5d0cd-5911-47c4-8e08-f4303a50af28
```

The receiving service should:

1. read the existing ID;
2. generate one if it is missing;
3. validate its length and format;
4. place it in the logging context;
5. propagate it to outgoing calls;
6. remove it from thread-local context when processing finishes.

With SLF4J MDC:

```java
String correlationId = request.getHeader("X-Correlation-ID");

if (correlationId == null || correlationId.isBlank()) {
    correlationId = UUID.randomUUID().toString();
}

try (MDC.MDCCloseable ignored =
             MDC.putCloseable("correlationId", correlationId)) {

    filterChain.doFilter(request, response);
}
```

The log format can include the MDC field:

```text
%date %-5level [%X{correlationId}] %logger - %message%n
```

Every outgoing HTTP request or message should propagate the same ID:

```java
request.header("X-Correlation-ID", correlationId);
```

For asynchronous processing, MDC requires special attention because it is commonly based on `ThreadLocal`. Context does not automatically follow work moved to another executor thread.

```java
Map<String, String> context = MDC.getCopyOfContextMap();

executor.submit(() -> {
    try {
        if (context != null) {
            MDC.setContextMap(context);
        }

        executeTask();
    } finally {
        MDC.clear();
    }
});
```

Modern distributed tracing normally uses standard trace context, such as W3C `traceparent`, with tools like OpenTelemetry. A tracing system distinguishes:

* **trace ID**: identifies the complete distributed request;
* **span ID**: identifies one operation within that request;
* **correlation/business ID**: may identify a payment, order, claim, or other business flow.

Structured logs should include trace and span identifiers so logs can be connected with metrics and distributed traces.
