# Proxy y ciclo de vida del proxy en Spring AOP

## 1. ¿Qué es un proxy?

Un **proxy** es un objeto intermediario que se coloca delante del objeto real administrado por Spring.

En lugar de llamar directamente al servicio:

```text
Controller → PaymentService
```

la llamada pasa primero por el proxy:

```text
Controller → Proxy → PaymentService real
```

El proxy puede ejecutar comportamiento adicional antes y después del método real:

```text
Controller
    ↓
Proxy
    ├─ Antes: inicia una transacción
    ↓
PaymentService.create()
    ↓
Proxy
    ├─ Después: confirma la transacción
    └─ Si hay error: hace rollback
```

Este mecanismo permite implementar funcionalidades transversales sin introducir su lógica dentro del método de negocio.

Ejemplos:

* `@Transactional`: transacciones.
* `@PreAuthorize`: autorización.
* `@Cacheable`: caché.
* `@Async`: ejecución asíncrona.
* `@Retryable`: reintentos.
* Logging, métricas y auditoría mediante aspectos.

---

# 2. ¿Qué es AOP?

AOP significa **Aspect-Oriented Programming**, traducido como **programación orientada a aspectos**.

Su objetivo es separar las responsabilidades transversales de la lógica de negocio.

Por ejemplo, el método:

```java
public Payment create(PaymentRequest request) {
    validate(request);
    return repository.save(Payment.from(request));
}
```

debería concentrarse en crear el pago.

Sin AOP, podría terminar mezclando responsabilidades:

```java
public Payment create(PaymentRequest request) {
    log.info("Starting payment creation");

    transactionManager.begin();

    long start = System.nanoTime();

    try {
        checkAuthorization();
        validate(request);

        Payment payment =
                repository.save(Payment.from(request));

        transactionManager.commit();

        return payment;
    } catch (Exception exception) {
        transactionManager.rollback();
        throw exception;
    } finally {
        metrics.record(System.nanoTime() - start);
    }
}
```

Con Spring AOP, esas responsabilidades pueden implementarse externamente:

```java
@Transactional
@PreAuthorize("hasAuthority('PAYMENT_CREATE')")
public Payment create(PaymentRequest request) {
    validate(request);
    return repository.save(Payment.from(request));
}
```

El método contiene la lógica de negocio, mientras los proxies aplican transacciones y seguridad.

# 3. Conceptos principales de AOP

## Aspect

Un **aspecto** encapsula una responsabilidad transversal.

Ejemplo:

```java
@Aspect
@Component
public class ExecutionTimeAspect {

    @Around(
        "execution(* com.example.payment.service..*(..))"
    )
    public Object measureExecutionTime(
            ProceedingJoinPoint joinPoint
    ) throws Throwable {

        long start = System.nanoTime();

        try {
            return joinPoint.proceed();
        } finally {
            long elapsed =
                    System.nanoTime() - start;

            System.out.println(
                    "Execution time: " + elapsed
            );
        }
    }
}
```

Aquí, el aspecto mide el tiempo de ejecución de los servicios.

## Join point

Un **punto de unión** es un punto de ejecución donde puede aplicarse un aspecto.

En Spring AOP, normalmente es la ejecución de un método de un bean administrado por Spring.

Por ejemplo:

```java
paymentService.create(request);
```

## Pointcut

Un **punto de corte** define qué métodos serán interceptados.

```java
execution(* com.example.payment.service..*(..))
```

Significa, aproximadamente:

> Cualquier método, con cualquier retorno y parámetros, dentro del paquete `service` y sus subpaquetes.

También se puede seleccionar por anotación:

```java
@Around("@annotation(Auditable)")
```

## Advice

Un **advice** es el código ejecutado alrededor del método seleccionado.

Tipos principales:

| Advice            | Momento de ejecución                    |
| ----------------- | --------------------------------------- |
| `@Before`         | Antes del método                        |
| `@After`          | Después del método, incluso si falla    |
| `@AfterReturning` | Después de retornar correctamente       |
| `@AfterThrowing`  | Después de lanzar una excepción         |
| `@Around`         | Antes y después; controla la invocación |

## Target

El **target** u objeto objetivo es la instancia real que contiene la lógica de negocio:

```java
PaymentService
```

## Proxy

El proxy es el intermediario creado por Spring:

```text
PaymentServiceProxy → PaymentService objetivo
```

El resto de la aplicación normalmente recibe el proxy, no una referencia directa al objeto objetivo.

# 4. Ciclo de vida de un proxy en Spring AOP

Supongamos este servicio:

```java
@Service
public class PaymentService {

    private final PaymentRepository repository;

    public PaymentService(
            PaymentRepository repository
    ) {
        this.repository = repository;
    }

    @Transactional
    public Payment create(
            PaymentRequest request
    ) {
        return repository.save(
                Payment.from(request)
        );
    }
}
```

## Paso 1: Spring prepara el contexto

Al iniciar la aplicación:

```java
SpringApplication.run(
        PaymentApplication.class,
        args
);
```

Spring crea el `ApplicationContext`.

Antes de crear la mayoría de los beans:

* procesa las configuraciones;
* registra las definiciones de beans;
* registra los `BeanPostProcessor`;
* registra la infraestructura de AOP;
* registra la infraestructura transaccional.

La definición del bean todavía no es necesariamente la instancia:

```text
BeanDefinition de PaymentService
```

La definición contiene información como:

* clase del bean;
* nombre;
* alcance;
* dependencias;
* métodos de inicialización;
* configuración de creación.

## Paso 2: Spring instancia el objeto real

Spring llama al constructor:

```java
new PaymentService(paymentRepository);
```

En este momento se crea el objeto objetivo:

```text
PaymentService real
```

Con constructor injection, las dependencias obligatorias se entregan durante esta etapa.

## Paso 3: Spring realiza la inyección restante

Si existen dependencias por setter o campo, se asignan después de la construcción.

Por ejemplo:

```java
@Autowired
private AuditService auditService;
```

Conceptualmente:

```text
Construcción
    ↓
Inyección de dependencias
```

Por eso, durante el constructor, una dependencia inyectada por campo todavía podría ser `null`.

## Paso 4: Se ejecutan callbacks de inicialización

Una vez inyectadas las dependencias, pueden ejecutarse:

```java
@PostConstruct
public void initialize() {
}
```

También existen:

* `InitializingBean.afterPropertiesSet()`
* métodos `initMethod` configurados en `@Bean`

En este punto hay que tener cuidado: no se debe asumir que una llamada interna desde `@PostConstruct` pasará por el proxy AOP final.

## Paso 5: Los `BeanPostProcessor` inspeccionan el bean

Spring pasa el bean por los objetos `BeanPostProcessor`.

Simplificadamente:

```java
postProcessBeforeInitialization(bean);
postProcessAfterInitialization(bean);
```

La infraestructura de auto-proxying utiliza un `BeanPostProcessor` para determinar si el bean necesita ser interceptado.

Por ejemplo, puede detectar:

```java
@Transactional
```

o verificar si algún pointcut de un `@Aspect` coincide con los métodos del bean.

## Paso 6: Spring crea el proxy

Si el bean necesita interceptores, Spring crea un proxy:

```text
Proxy de PaymentService
         ↓
PaymentService real
```

El proxy contiene una cadena de interceptores, por ejemplo:

```text
SecurityInterceptor
        ↓
TransactionInterceptor
        ↓
MetricsInterceptor
        ↓
PaymentService.create()
```

El orden depende de la configuración de los interceptores.

## Paso 7: Spring registra el proxy como bean expuesto

Este es un punto fundamental.

Aunque Spring creó primero el objeto real, la referencia que normalmente registra y entrega a otros beans es el proxy:

```text
ApplicationContext
    paymentService → PaymentServiceProxy
```

Por eso, cuando el controlador recibe el servicio:

```java
@RestController
public class PaymentController {

    private final PaymentService paymentService;

    public PaymentController(
            PaymentService paymentService
    ) {
        this.paymentService = paymentService;
    }
}
```

`paymentService` puede no ser la instancia directa de `PaymentService`. Puede ser un proxy que delega en ella.

## Paso 8: La aplicación comienza a recibir llamadas

Cuando el controlador ejecuta:

```java
paymentService.create(request);
```

la llamada entra por el proxy.

```text
Controller
    ↓
Proxy
    ↓
TransactionInterceptor
    ↓
PaymentService real
```

Para `@Transactional`, el interceptor:

1. Lee la configuración transaccional.
2. Obtiene o crea una transacción.
3. Invoca el método real.
4. Ejecuta `commit` si termina correctamente.
5. Ejecuta `rollback` si ocurre una excepción que lo requiere.
6. Devuelve el resultado o propaga la excepción.

# 5. Ejecución de `@Transactional`

Método:

```java
@Transactional
public Payment create(
        PaymentRequest request
) {
    return repository.save(
            Payment.from(request)
    );
}
```

La anotación no contiene por sí sola la lógica transaccional. Es metadato interpretado por Spring.

La ejecución conceptual es:

```java
public Object invoke(MethodInvocation invocation) {
    TransactionStatus transaction =
            transactionManager.begin();

    try {
        Object result = invocation.proceed();

        transactionManager.commit(transaction);

        return result;
    } catch (Throwable exception) {
        transactionManager.rollback(transaction);

        throw exception;
    }
}
```

La implementación real es más compleja porque considera:

* Propagación: `REQUIRED`, `REQUIRES_NEW`, etc.
* Nivel de aislamiento.
* `readOnly`.
* Timeout.
* Reglas de rollback.
* Transacciones existentes.
* El `PlatformTransactionManager` seleccionado.

# 6. Tipos de proxy utilizados por Spring

## JDK Dynamic Proxy

El proxy dinámico de Java trabaja principalmente mediante interfaces.

```java
public interface PaymentService {
    Payment create(PaymentRequest request);
}
```

```java
@Service
public class PaymentServiceImpl
        implements PaymentService {
}
```

Conceptualmente:

```text
PaymentService
      ↑
JDK Proxy
      ↓
PaymentServiceImpl
```

El objeto inyectado implementa `PaymentService`, pero no necesariamente es una instancia directa de `PaymentServiceImpl`.

```java
paymentService instanceof PaymentService
// true
```

El proxy es generado mediante APIs estándar de Java:

```java
java.lang.reflect.Proxy
```

## Proxy basado en clase

Cuando es necesario proxyficar la clase concreta, Spring puede crear una subclase dinámica:

```text
PaymentService
      ↑
PaymentService$$SpringCGLIB$$...
```

Conceptualmente:

```java
class GeneratedProxy extends PaymentService {
    // Intercepta métodos
}
```

Este tipo de proxy no depende de una interfaz.

En versiones modernas de Spring, la generación de proxies de clase utiliza una versión de CGLIB integrada dentro de Spring Core.

### Limitaciones

Los proxies basados en subclases no pueden interceptar correctamente:

* Clases `final`.
* Métodos `final`.
* Métodos `private`.
* Llamadas que no pasan por el proxy.

Por ejemplo:

```java
@Transactional
private void savePayment() {
}
```

No es un buen punto de interceptación para Spring AOP.

# 7. El problema de la auto-invocación

Este es uno de los problemas más importantes de Spring AOP.

```java
@Service
public class PaymentService {

    public void processPayment(
            PaymentRequest request
    ) {
        validate(request);
        savePayment(request);
    }

    @Transactional
    public void savePayment(
            PaymentRequest request
    ) {
        repository.save(
                Payment.from(request)
        );
    }
}
```

Un controlador llama:

```java
paymentService.processPayment(request);
```

Flujo:

```text
Controller
    ↓
Proxy
    ↓
PaymentService.processPayment()
    ↓
this.savePayment()
```

La llamada:

```java
savePayment(request);
```

equivale a:

```java
this.savePayment(request);
```

Esa llamada se realiza directamente dentro del objeto real. No regresa al proxy.

Por lo tanto:

```java
@Transactional
public void savePayment(...)
```

podría ejecutarse sin que el proxy inicie una nueva transacción.

## Por qué sucede

El proxy solamente intercepta llamadas que entran desde afuera:

```text
Otro bean → Proxy → Objeto real
```

No puede interceptar una llamada que permanece dentro del mismo objeto:

```text
Objeto real → this.otroMetodo()
```

## Solución recomendada: separar responsabilidades

```java
@Service
public class PaymentProcessor {

    private final PaymentWriter paymentWriter;

    public PaymentProcessor(
            PaymentWriter paymentWriter
    ) {
        this.paymentWriter = paymentWriter;
    }

    public void processPayment(
            PaymentRequest request
    ) {
        validate(request);
        paymentWriter.savePayment(request);
    }
}
```

```java
@Service
public class PaymentWriter {

    private final PaymentRepository repository;

    public PaymentWriter(
            PaymentRepository repository
    ) {
        this.repository = repository;
    }

    @Transactional
    public Payment savePayment(
            PaymentRequest request
    ) {
        return repository.save(
                Payment.from(request)
        );
    }
}
```

Ahora el flujo sí atraviesa el proxy:

```text
PaymentProcessor
       ↓
PaymentWriter proxy
       ↓
TransactionInterceptor
       ↓
PaymentWriter real
```

Esta solución también suele mejorar la separación de responsabilidades.

# 8. Crear el objeto manualmente evita el proxy

Esto no obtiene el bean administrado por Spring:

```java
PaymentService service =
        new PaymentService(repository);
```

Es un objeto Java normal.

Por lo tanto, estas anotaciones no producirán automáticamente su comportamiento esperado:

```java
@Transactional
@Async
@Cacheable
@PreAuthorize
@Retryable
```

El objeto debe obtenerse mediante inyección:

```java
@Service
public class PaymentController {

    private final PaymentService service;

    public PaymentController(
            PaymentService service
    ) {
        this.service = service;
    }
}
```

La regla conceptual es:

> Para que Spring AOP intercepte una llamada, el objeto debe ser administrado por Spring y la llamada debe pasar por el proxy.

# 9. Proxy y pruebas unitarias

En una prueba unitaria:

```java
PaymentService service =
        new PaymentService(repository);
```

no se está probando el proxy. Se prueba solamente la lógica del servicio.

Esto es correcto para una prueba unitaria:

```java
@Test
void createsPayment() {
    PaymentRepository repository =
            mock(PaymentRepository.class);

    PaymentService service =
            new PaymentService(repository);

    service.create(request);

    verify(repository).save(any());
}
```

Sin embargo, esta prueba no demuestra que `@Transactional` funcione.

Para probar la integración transaccional se necesita un contexto de Spring:

```java
@SpringBootTest
class PaymentTransactionTest {

    @Autowired
    PaymentService service;

    @Test
    void rollsBackWhenCreationFails() {
        // Prueba de integración
    }
}
```

Aquí Spring inyecta el bean administrado, posiblemente representado por un proxy.

# 10. Proxy y tipos de anotaciones

| Anotación             | Infraestructura principal | Interceptor aplicado                 |
| --------------------- | ------------------------- | ------------------------------------ |
| `@Transactional`      | Spring Transaction        | Transacciones                        |
| `@PreAuthorize`       | Spring Security           | Autorización                         |
| `@Cacheable`          | Spring Cache              | Caché                                |
| `@Async`              | Spring Task Execution     | Ejecución asíncrona                  |
| `@Retryable`          | Spring Retry              | Reintentos                           |
| Aspecto personalizado | Spring AOP                | Lógica definida por el desarrollador |

Cada anotación necesita que su infraestructura esté habilitada.

Por ejemplo:

```java
@EnableMethodSecurity
```

para determinadas anotaciones de seguridad:

```java
@PreAuthorize("hasRole('ADMIN')")
```

Para caché:

```java
@EnableCaching
```

Para asincronía:

```java
@EnableAsync
```

La sola presencia de una anotación no garantiza que exista el procesador que la interpreta.

# 11. Ejemplo de un aspecto personalizado

Dependencia:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-aop</artifactId>
</dependency>
```

Aspecto:

```java
@Aspect
@Component
public class LoggingAspect {

    private static final Logger log =
            LoggerFactory.getLogger(LoggingAspect.class);

    @Around(
        "execution(* com.example.payment.service..*(..))"
    )
    public Object logExecution(
            ProceedingJoinPoint joinPoint
    ) throws Throwable {

        String methodName =
                joinPoint.getSignature().toShortString();

        log.info("Starting {}", methodName);

        try {
            Object result = joinPoint.proceed();

            log.info("Completed {}", methodName);

            return result;
        } catch (Exception exception) {
            log.error(
                    "Failed {}",
                    methodName,
                    exception
            );

            throw exception;
        }
    }
}
```

Flujo:

```text
Caller
   ↓
Spring AOP Proxy
   ↓
LoggingAspect: antes
   ↓
Servicio real
   ↓
LoggingAspect: después
   ↓
Caller
```

`joinPoint.proceed()` es el punto donde el aspecto permite continuar hacia:

* otro interceptor;
* otro aspecto;
* o finalmente el método real.

Si un `@Around` no llama a `proceed()`, el método real no se ejecuta.

# 12. Resumen del ciclo de vida

| Etapa                 | Qué sucede                                         |
| --------------------- | -------------------------------------------------- |
| 1. Configuración      | Spring carga configuración y registra definiciones |
| 2. Instanciación      | Spring llama al constructor del bean               |
| 3. Inyección          | Se asignan sus dependencias                        |
| 4. Inicialización     | Se ejecutan callbacks como `@PostConstruct`        |
| 5. Postprocesamiento  | Los `BeanPostProcessor` inspeccionan el bean       |
| 6. Creación del proxy | Spring agrega los interceptores necesarios         |
| 7. Registro           | El contexto expone normalmente el proxy            |
| 8. Invocación         | Las llamadas externas pasan por los interceptores  |
| 9. Método real        | El proxy delega en el objeto objetivo              |
| 10. Resultado         | Los interceptores procesan retorno o excepción     |

La idea esencial es:

```text
Bean real = lógica de negocio
Proxy = comportamiento transversal
```

Y la condición fundamental es:

```text
Bean administrado por Spring
          +
Llamada que entra a través del proxy
          =
AOP aplicado correctamente
```
